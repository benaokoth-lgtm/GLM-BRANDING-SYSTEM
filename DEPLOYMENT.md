# Deploying to cPanel — api.glmgroup.co.ke + pos.glmgroup.co.ke

Two pieces are hosted, both **prebuilt and committed under `deploy/`** — nothing is built on the server:

| Folder | What it is | Where it runs |
|---|---|---|
| `deploy/api/` | One bundled `server.js` (shared code inlined), a tiny `package.json` (only `@prisma/client` + `prisma`), and the Prisma schema pre-set to PostgreSQL | cPanel **Setup Node.js App** → this folder is the *Application root* |
| `deploy/web/` | The static React build (API URL baked in) + `.htaccess` for client-side routes | Copied to the `pos.glmgroup.co.ke` document root |

**Why not build on the server?** cPanel's Node.js Selector replaces the app root's `node_modules` with a symlink into its own virtual env, which doesn't cooperate with this repo's npm-workspaces monorepo (npm sees one package and installs nothing). A slim, prebuilt app root is the layout the Selector is designed for. The monorepo itself is unchanged for local development.

## One-time setup

### 1. Database
cPanel → **PostgreSQL Databases**: create a database (no spaces in the name!), a user, and add the user to the database with all privileges. The connection string is:

```
postgresql://DBUSER:PASSWORD@127.0.0.1:5432/DBNAME
```

Use `127.0.0.1`, not `localhost` (this host rejects IPv6 `::1`). If the password contains `@ : / ? # %`, percent-encode those characters.

### 2. Git
cPanel → **Git™ Version Control** → Create: clone URL `https://github.com/benaokoth-lgtm/GLM-BRANDING-SYSTEM.git`, path `/home/glmgroup/repositories/glm-branding-pos-system`, branch `main`.

### 3. The API's Node.js App
cPanel → **Setup Node.js App** → Create (or edit) the application:

- **Node.js version**: 18 (or newer)
- **Application mode**: Production
- **Application root**: `repositories/glm-branding-pos-system/deploy/api`
- **Application URL**: `api.glmgroup.co.ke`
- **Application startup file**: `server.js`

**Environment variables — one row per variable, raw value only** (no `export`, no quotes, never several in one value):

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_URL` | the connection string from step 1 |
| `JWT_SECRET` | a long random string — generate once with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and keep it; changing it logs everyone out |
| `CORS_ORIGINS` | `https://pos.glmgroup.co.ke` |

No `PORT` — Passenger assigns it. Optional (each feature disables itself cleanly if unset): `SMTP_*` (**older installs only** — email is now set up in Master Data → Email) and the `MPESA_*` set (**older installs only** — M-Pesa is now configured in Master Data → M-Pesa instead; see `apps/api/.env.example`; `MPESA_CALLBACK_URL` must be `https://api.glmgroup.co.ke/api/mpesa/callback`).

Save, then click **Run NPM Install** (this installs Prisma and generates its client), then **Restart**.

### 4. The web subdomain
cPanel → **Domains**: create `pos.glmgroup.co.ke`; its document root should be `/home/glmgroup/pos.glmgroup.co.ke` (what `.cpanel.yml` copies into). An old PHP point-of-sale system once lived here and must be moved out of this folder first: `.cpanel.yml` refuses to deploy into any folder that has an `index.php`.

### 5. First deploy
**Git Version Control → Pull or Deploy → Update from Remote → Deploy HEAD Commit.** This copies `deploy/web` into the subdomain and restarts the API (`.cpanel.yml`).

### 6. Create the database tables and the first Admin
In cPanel **Terminal**, activate the app's environment (copy the exact `source …/activate` line shown at the top of the Setup Node.js App page), then:

```bash
cd /home/glmgroup/repositories/glm-branding-pos-system/deploy/api
export DATABASE_URL="postgresql://DBUSER:PASSWORD@127.0.0.1:5432/DBNAME"
npm run db:push
node seed-admin.js "Your Name"
```

`seed-admin.js` prints one random Admin PIN, once — keep it. Do **not** run the dev seed (`apps/api/prisma/seed.ts`) in production: it wipes every table and creates demo users with hard-coded PINs. Log in, then set up Company Info, Staff, Services and Materials under Master Data.

The chart of accounts builds itself the first time anyone opens Accounting (or when the API starts), and asset depreciation runs on its own each month. To start the books properly, an Admin enters **opening balances** (bank, cash on hand, M-Pesa float, owner's capital) once under Accounting → Journals → *Opening balance*, and tops up the petty-cash float under Finance → Petty Cash. Check the books at any time with Accounting → Books Check, or from the Terminal:

**Purchases, purchase orders and reconciliation.** In Stock, *Stock Requisition* is now **Purchases Requisition** and *Stock Approval* is **Purchases Approval**. Each requisition line has an **expected unit price** (blank = the last price paid for that material). A purchase is now a **purchase order** with a reference (PO-0001…) and **any number of lines** — a material, the quantity bought and the real unit price from the supplier's invoice; raising one against an approved requisition pre-fills its remaining lines. It is *held*: stock does not go up until the **store manager receives it** (new permission **Stores: receive purchased goods**, given to Supervisor, Finance Manager and General Manager on first start; change it under Master Data → Roles & Access), entering the quantity that physically arrived on each line — stock goes up by what was *received*, which may be less than was invoiced. Whoever captured a purchase cannot receive it. A new **Purchases Reconciliation** tab compares, for every approved requisition reference, what was requisitioned with what was bought and what was received: quantity variance, short deliveries, price variance and total variance per line and per requisition, split into a price part and a quantity part that add up to the total; purchases with no requisition are listed apart. Purchases from before this change are converted automatically (each becomes a one-line purchase order with its own PO number), and a China import is now one purchase order with a line per material. Run `npm run db:push` once: it adds the purchase-line, expected-price, PO-reference and receiving columns (the old single-material columns on a purchase become optional — nothing is dropped).

**Business heads.** Master Data → **Business Heads** holds the lines of business income is reported under — DTF Printing, UV Printing, Laser Engraving, Large Format Printing, Embroidery and General Order are created on first start, and Admin can add, rename, retire or (when empty) remove them. Every service belongs to one (chosen in Service Price List; existing services are placed by name until you change them, and anything that does not fit goes to General Order); a material sold over the counter counts as General Order. Reports → **Sales by Business Head** shows orders and sales (excluding VAT, after discounts, before credit notes) per head, with the services inside each.

**Module row dims while you work inside a module; film and artwork orders are separate.** Once you click one of a module's sub-items (Finance → Expenses, Stock → Purchases, Reports → Sales by Business Head, My Orders → Invoices…), the row of modules above is dimmed to half strength — still visible and clickable, and back to full strength when the mouse is over it. Clicking a module brings the row back and returns that module to its starting view. In My Orders and All Orders the order filter is now *All orders / General / Film / Artwork* (the Type column says Film or Artwork too). No database change.

**My Orders by business head; Production and Quality control kept apart by head.** My Orders and All Orders have one row of business heads (*All orders, DTF Printing, Embroidery, … General Order*, each with its count). DTF Printing opens a second row: *All DTF Printing, Film sales, Artwork sales* (and *Other DTF lines* if a general order happens to carry a DTF line). Under the chosen head the usual Orders / Invoices / Quotations split applies; an order with lines in two heads appears under both. In Production (waiting to be assigned and jobs in hand) and in Quality control (awaiting inspection and the inspection history) the orders are listed under a heading per business head — DTF Printing split into *Film sales* and *Artwork sales* — each order once, under the head that carries most of its value. No database change.

**Payroll now follows the Kenyan statutory rules — no database change.** Before, PAYE was charged on gross pay, and the *whole* 12% NSSF and 3% housing levy (the employee's and the employer's shares together) were taken from the employee's pay. Now, for an employee: **NSSF** is 6% of pay up to NSSF's Upper Earnings Limit for the pay date (KES 18,000 from Feb 2023, 36,000 from Feb 2024, 72,000 from Feb 2025, 108,000 from Feb 2026 — so at most 6,480 a month from Feb 2026), **SHIF** is 2.75% of gross pay (minimum KES 300) and the **Affordable Housing Levy** is 1.5% of gross pay; these three are deducted from gross pay first, **PAYE is charged on what is left** (taxable pay) by the monthly bands (10% to 24,000, 25% to 32,333, 30% to 500,000, 32.5% to 800,000, 35% above), less the KES 2,400 personal relief (never below zero). The **employer** matches NSSF (6%) and the housing levy (1.5%) *on top of* the pay: an extra cost, shown on the NSSF tab and on payslips, and booked as wages expense with the liability owed to NSSF and the levy fund — so the employee's net pay goes **up** compared with before, and wages expense in the books includes the employer's share. Everything is worked out when read, so **pay logged earlier is recalculated by the new rules** (the P9 and payslips follow). The rates and limits are constants at the top of `packages/shared/src/tax.ts` — **have your accountant check them against the current NSSF, KRA and SHA notices** (they change) and tell me if any differ. The P9 shows gross pay, NSSF, SHIF, housing levy, taxable pay, tax charged, personal relief and PAYE month by month.

**Employee details, payroll and P9 printing — needs `npm run db:push` (VPS: `update.sh` does it).** Compliance has two new tabs. **Employees** records each person's **National ID** (7–8 digits), **KRA PIN** (a letter, nine digits and a letter; stored in capitals) and **SHIF registration number** — optional, tidied on the way in, and the National ID and KRA PIN cannot belong to two people. The company's own **KRA PIN** goes under Master Data → Company Info (it prints as the employer's PIN). **Payroll** now has *Print payroll (A4)* for the dates chosen (landscape register with each person's National ID, KRA PIN and SHIF number), *Print all payslips* and a *Payslip* button on every pay entry (one A4 page each). **P9** lists each employee's gross pay and PAYE for a chosen year and prints a landscape A4 P9 tax deduction card per employee (or all of them): month by month gross pay, NSSF, SHIF, housing levy, taxable pay, tax charged, personal relief and PAYE, worked out exactly as the payroll worked it out when the pay was logged. Casual staff carry no PAYE, so they have no P9. Printing also fixes one thing: an older corporate invoice that had been paid in full (status "Order") no longer prints with the heading QUOTATION. **Invoices and quotations print on A4 in the house layout — walk-in ones too; only a walk-in order paid in full prints on the thermal receipt printer** (so a walk-in sale left with a balance prints as an A4 invoice). New columns: `User.nationalId`, `User.kraPin`, `User.shifNumber` (empty by default) and `Setting.kraPin`.

**Staff names in three parts — needs `npm run db:push` (VPS: `update.sh` does it).** Master Data → Staff & Users now captures a name as **first name** and **surname** (both compulsory) and an optional **middle name**; the full name used everywhere else (login screen, orders, reports) is the three joined, and two people cannot share the same full name. Existing staff get an *Edit name* button in the list; on first start their old full name is split once (first word → first name, last word → surname, anything between → middle name), and anyone with a one-word name (for example just "BEN") shows a *Surname needed* tag until an Admin completes it. Three new columns on the user table (`firstName`, `middleName`, `lastName`, empty by default). Documents already issued keep the name they were issued with.

**All Orders: the four summary figures open.** *Total orders*, *In production*, *Pending balance* and *Overdue invoices* at the top of All Orders are now clickable: each opens a table of the orders behind it (order, date, client, staff, status, stage, due date, total, paid, balance, with totals), and clicking an order opens it. Pending balance lists biggest balance first and Overdue invoices oldest first. The figures follow the business-head selection above them. A quotation is an offer, not money owed or work in hand, so it is no longer counted in *In production* or *Pending balance*. No database change.

**VAT is automatic — sales, purchases and expenses — needs `npm run db:push`.** Compliance → VAT is worked out from the books for whatever period you pick, with nothing to claim by hand: **Output VAT** (every sale — walk-ins and every corporate order past Quotation — less credit notes, plus debit notes), **Input VAT** (the VAT in every purchase and expense under a head that carries VAT) and **Net VAT payable to KRA** (output less input; a negative figure shows as refundable / carried forward). Which spending carries VAT is set once per expense head, in the *VAT treatment by expense head* panel on the same tab (Yes / No, with a *back to standing answer* button); every purchase and expense under the head follows, past and future. Standing answers: materials & consumables, stock, transport, utilities, equipment maintenance, office supplies, courier, airtime/data, cleaning and **Outsourced Services (the supplier's VAT is claimed back)** carry VAT; casual labour, wages, bank charges, refreshments, commission, miscellaneous and anything unrecognised do not. The VAT is 16/116 of what was paid and is taken out of the cost and posted to the VAT account, so **cost of sales, expenses and profit in the P&L now exclude it — including for expenses already recorded, so past profit figures rise by the VAT in them**; the books stay balanced and Reconciliation counts the VAT as part of the expense. Outsourced job profit (Production → Outsourced jobs, order costing) likewise takes the VAT out of the supplier's bill. Rows with no invoice number are counted but flagged — keep the supplier's tax invoice for every claim. Stock purchases with no expense behind them (import batches) carry no VAT. Two new columns: `ExpenseHead.vatApplicable` (null = standing answer) and the now-unused `Expense.vatAmount` (kept so no data is dropped). Sales by Business Head keeps showing purchase costs as invoiced (VAT included).

**Commission on/off switch — needs `npm run db:push`.** There is one new column (`CommissionSettings.enabled`, default off), so run `npm run db:push` after deploying. **Commission is OFF after this deploy** until an Admin switches it on in *Master Data → Company Info → Sales commission → Switch on* (and it can be switched off the same way at any time). While it is off the Commission module is hidden from everyone, the "who sourced this client" box is gone from the order forms, a claim sent by an old browser tab is ignored, no order is credited to anyone and no client is taken on, and the commission API answers "switched off". Nothing is deleted: rates, client ownership, statements and payouts are all kept and are back when it is switched on again. Film and artwork commission is worked out from the payments received in each month, so the cleanest time to start is the 1st of a month; clients are only credited, and orders only counted for the 12-month window, from the day it is switched on.

**One Orders module.** *My Orders* is gone — it duplicated All Orders. The *All | Invoices | Quotations* row (with the Not yet completed / Completed split under Invoices, and the Due date column) now lives in *All Orders*, which sits where My Orders used to be in the top row. People who may see every order get the whole list with the summary figures and a staff filter; a member of staff gets the same screen, called *Orders*, with only their own orders. The old status drop-down is replaced by the Invoices / Quotations row. Order capture screens now land here after saving, and a saved link to *My Orders* redirects to it. No database change.

**My Orders adds up.** In My Orders and All Orders every order is now counted once, under one business head — the head of the service carrying most of its value (blank garments and other materials only decide it when an order has no service line, so a shirt with embroidery is an Embroidery job). The head chips (DTF Printing, UV Printing, Laser Engraving, Large Format Printing, Embroidery, General Order — always listed, plus any other head that has orders) therefore add up exactly to *All orders*. The Orders / Invoices / Quotations row no longer has an *Orders* chip: it is *All | Invoices | Quotations*, where *All* shows paid-in-full orders, invoices and quotations together (the Status column tells them apart). Production and Quality control use the same head for their headings. No database change.

**All Orders is out of Finance.** The Finance module no longer has an All Orders tab (Quotation, Invoice, Payments, Expenses, Petty Cash and Asset Register remain). People who may see every order get All Orders as its own module in the top row instead, so nobody loses the view. "View in All Orders" after creating a quotation or invoice takes you there. No database change.

**Reports and DTF history, a level deeper.** *Accounts Receivable* is gone from Reports (it lives in Accounting → Receivables). In Reports → *Sales by Business Head*, click a head (or the Shared row) to open the sales lines, purchase lines and expenses behind its figures for the period — click an order in it to open the order. In DTF, **Artwork Jobs** and **Film Sales** now list a day at a time: for artwork, the number of jobs printed, pieces, metres used, average price per job, average recommended and final price per piece, and the total, paid and balance; for film, the sales, metres sold, average price per metre, total, paid and balance. Click a date to see every individual order of that day, and an order to open it (an admin can still delete a bad entry, and a manager can mark a film sale paid, from the day's list). Money comes from the orders, so a payment taken later through the order shows here. No database change.

**Artwork jobs: heat press, lower prices, approvals and discount impact.** (1) An artwork job cannot be processed without a **heat press fee** — the Heat press field is now required (no "None"). (2) The price per piece may now be entered **below** the recommended price, but not under the per-piece floor (DTF → Setup, *Minimum price / piece*). A lower price **is the discount**: no other discount applies, no commission premium is earned on it, and it **goes to a DTF manager for approval first** — until approved the job cannot be paid for, queued in Production or assigned (its film metres stay reserved on the roll, its revenue is not counted), it shows in My Orders as *Awaiting price approval*, and no receipt is printed. Managers (DTF manager permission) decide under DTF → **Price Approvals**, seeing the discount and the roll's profit as it stands and as it would be if approved; whoever captured the job cannot decide it. Approving releases it; rejecting (with a reason) removes the order and job and returns the film to the roll, keeping the request as the record. (3) **Discount impact on roll profitability**: DTF → Dashboard has a new *What discounts cost — roll by roll* table (revenue at full price, discounts given, % of revenue, revenue, roll cost, profit at full price, profit, profit lost), each roll card shows its discounts and the share of profit they took, and the artwork page shows the effect of a lower price on the roll before it is sent. A *discount* here is an artwork job charged below the recommended price (approved ones only) — **film orders are not touched by any of this**: film keeps its own price rules (a minimum price, no approval) and is not counted as a discount. Run `npm run db:push` once: it adds the approval status on artwork jobs and the price-approvals table.

**Profit & Loss drill-down.** In Accounting → Profit & Loss, click any income, cost-of-sales or expense account to open the transactions behind its figure for the period on screen (date, source, reference, detail, debit, credit and the amount it adds to the line, with a total that equals the P&L line); click again to close. In Production → Orders & jobs the date is now the second column. No database change.

**Faster order lines.** On General Order (and corporate quotations and invoices): each line has **one Discount box with a % / Ksh switch** (a line carries one kind of discount or the other) instead of two columns; every line shows its **Line total**; a **duplicate** button copies a line right under itself; the item search opens with **your recent picks** first (the last few you sold, remembered in this browser); and the keyboard carries the whole order — picking an item jumps to Quantity, **Enter** moves to the next box, and Enter in the last box of a line opens the next line (adding one at the end). The **order-level discount** is hidden behind an *Add order discount* link until it is needed. No database change.

**Client name and phone are optional on walk-in sales.** On General Order, Film Order and Artwork Order the client's name and phone number can be left blank; a blank name is recorded as **Walk-in**. They become mandatory only when a client is being credited to a staff member for commission (the "brought this client in" box): then both a real name (not blank, not "Walk-in") and a phone number are needed, so the client can be recognised on their next order. An anonymous "Walk-in" can never be credited to anyone. No database change.

**Order lines pick from one searchable list.** On a General Order (and on corporate quotations and invoices) each line now has a single *Item or service* picker instead of the Type and Material/Service dropdowns: type part of a name to search the Service Price List and the Stock Price List together (services and items are listed under their own headings, with price and stock on hand), then click it or press Enter. The kind of line follows from what is picked (a service sold by the metre becomes a per-metre line). Quantity, unit price and both discounts are unchanged. A new line starts empty; a line with nothing picked is ignored when the order is saved, and an order needs at least one real line. No database change.

**One Profit & Loss, in Accounting.** The P&L tab under Finance is gone. Accounting → Profit & Loss now carries its dashboard — Revenue (accrual), Revenue (cash received), Gross profit and Net profit, each compared with the period just before it, plus the six-month revenue and net-profit chart — and every figure comes from the books, so the cards always agree with the statement under them (the old Finance P&L was built separately from orders and could differ). Revenue (cash received) is the money actually received from customers in the period, VAT included. Anyone who had the P&L permission but no Accounting access still reaches it: they see just the Profit & Loss tab (the permission is now labelled *P&L (Accounting → Profit & Loss)* under Master Data → Roles & Access), and an old /pnl bookmark lands there. No database change.

**Invoices stay invoices.** An order captured with a balance is an invoice, and it now stays an invoice once it is paid in full — it is tracked through production to completion instead of turning back into an Order. In My Orders, the Invoices tab shows every invoice with its payment status and stage and can be filtered to *Not yet completed* or *Completed*; the Orders tab holds only orders that were paid in full when captured. A paid invoice no longer appears in Accounts Receivable (nothing is owed) and never shows as overdue. Invoices that were already turned back into Orders by the old behaviour stay as Orders — there is no record of which they were. No database change.

**Costs by business head.** Purchases and expenses can now be tagged to a business head, so Reports → **Sales by Business Head** shows sales, costs and margin for each line of business. A **material** has a usual business head (Master Data → Stock Price List, e.g. DTF film → DTF Printing); every **purchase-order line** is tagged to its material's head when captured and can be changed on the line (or afterwards, in the purchase history); every **expense** has an optional business head on capture and can be re-tagged in the Finance → Expenses list (no amendment request is needed — no amount changes); a **supplier bill for an outsourced job** takes the head of the contracted-out service automatically. In the report, costs are what was bought for the head (purchase lines) plus the expenses tagged to it, as recorded (VAT included — input VAT is not reclaimed); an expense that backs a purchase order is counted once, through the purchase; rejected purchases cost nothing; anything not tagged is shown apart as **Shared** (rent, wages, utilities and so on) and is not spread across the heads. Run `npm run db:push` once: it adds the business-head columns to materials, purchase lines and expenses. Existing purchases and expenses start untagged (Shared) — tag them to see their figures under a head.

**Sales commission.** A new **Commission** tab. Staff who capture orders see their own month (what they earned and why, what they sold, the clients credited to them); people with the new **Commission: rates, team statements & payouts** permission (Finance Manager and General Manager are given it automatically on first start; change it under Master Data → Roles & Access) also see the whole team, set the rates, manage client ownership, and approve and pay the month. Commission is earned on money *received* in the month, net of VAT, and credit notes reverse what had been paid:

- *Sales you source* — a banded percentage (marginal, like income tax) of a staff member's monthly net sales from clients credited to them. A client a staff member brings in (the "brought this client in" box when capturing an order — needs the client's phone number, or a corporate client) is credited to them for 12 months; during that time every order from that client counts for them whoever captures it, and nobody else can claim the client. A manager can credit older clients by hand, or release one, under Commission → Clients.
- *Film* — the capturing staff member earns a ladder percentage of the price per metre charged **above the base (the DTF minimum price, 400)**. The 500 ceiling is gone: film can be sold at any price at or above the minimum.
- *Artwork* — staff may now enter a price per piece **above** the system-recommended price (it can never be below it) and earn a percentage of the amount above the recommendation, nothing on the recommended price.

Film and artwork commission is earned as the customer pays (a half-paid order earns half). Every figure — the bands, the film ladder, the artwork percentage, the 12-month window — is editable under Commission → Rates; the starting values are placeholders because there is no sales history to calibrate against. Approving a month freezes it; **Mark paid** records an expense under the new *Sales Commission* head (account 5020), so it reaches the books and, when paid from petty cash, the float. Run `npm run db:push` once: it adds the commission tables, the sourcing columns on orders and the artwork "charged price" column; existing orders become "house" orders and earn no sourcing commission.

**Contracted-out (outsourced) services.** Eulogy printing, banners, screen printing and similar. In Master Data → Service Price List, tick *Contracted out* on a service and fill in the supplier, the supplier's usual price per unit (one price covering paper and printing, VAT included), and the mark-up as a percentage or a fixed amount per unit; *Set price to…* applies the result as the selling price (also VAT inclusive). On each order the supplier's real quote is entered on the line and the price follows it. The same `npm run db:push` adds the columns. Costs and mark-ups are only visible to roles with the new **See supplier costs & mark-ups** permission (Finance Manager and General Manager are given it automatically on first start; change it under Master Data → Roles & Access). Staff can still sell the service at the price-list price; the server withholds the cost fields from them. Supplier bills (paid in full, or a deposit with the balance owing) are recorded on the order and count as cost of sales; a contracted-out order is sent to its supplier from Production, received back, and then goes through Quality Control like any other.

**Email.** Set up by the Admin under **Master Data → Email** — no server variables needed. Click *Set up mail client settings* and copy in what cPanel shows for the mailbox (Email Accounts → *Connect Devices* → Secure SSL/TLS Settings): the username (the full address, e.g. `admin@glmgroup.co.ke`), the mailbox password, the incoming server (IMAP 993 / POP3 995 — kept for reference) and the **outgoing server with SMTP port 465** (`mail.glmgroup.co.ke`). **Save & send test** proves it works. The same account sends: staff login PINs, the Admin's PIN-reset code, and invoices or quotations emailed to clients. To email a person their login: Master Data → Staff & Users → add their email → **Email login PIN** (a new random PIN is generated and emailed; they must choose their own at first sign-in, and if the email fails their old PIN is left alone). Anyone with an email can also be created and emailed in one step. An install still on the old `SMTP_*` variables keeps working until the first save here.

**Production, quality control and requisitions.** The same `npm run db:push` adds their tables. It will warn that it drops the old `cogsPct` column (the cost-of-sales percentage, now replaced by actual purchases) — that is expected; answer `y`. On first start the API (a) gives any older stock requisitions a reference number (REQ-0001…) and turns each one's material into a line, and (b) grants the new Production / Quality permissions once: Staff can work the jobs they're assigned; Supervisor, Finance Manager and General Manager can assign staff and see productivity; Supervisor, Finance Manager and General Manager can inspect quality. Adjust them any time under Master Data → Roles & Access. Orders already in the system appear in Production's "Waiting to be assigned" list according to their current stage.

**M-Pesa.** Set up by the Admin under **Master Data → M-Pesa** — no server variables needed any more. Enter the Paybill/Till number, tick "Till" if it is one, the consumer key, consumer secret and passkey from Safaricom's Daraja portal, and this installation's public address (`https://api.glmgroup.co.ke`). **Save**, **Test the connection**, then **Switch on**. The secret and passkey are never shown again once saved. Start in *Sandbox*; change to *Production* with your live keys when ready. To also catch Paybill/Till payments made without a prompt, click **Register these addresses with Safaricom** (needs a Production Paybill/Till). Without registering, upload the M-Pesa statement under Accounting → M-Pesa Matching — matching works from that too. (An install already running on the old `MPESA_*` variables keeps working until the first save in Master Data, which carries those values over.)

**Forgot a PIN, or a correct PIN "doesn't work"?** Five wrong attempts lock a user for 15 minutes. From the same folder and environment as above:

```bash
node reset-pin.js --list                 # who exists, and who is locked
node reset-pin.js "Your Name"            # new random 4-digit PIN (also clears any lockout)
node reset-pin.js "Your Name" 4821       # or choose the PIN yourself
```

**Emailed reset for the Admin ("Admin: forgot PIN?" on the login screen).** Give the Admin a recovery email once, from the same folder and environment:

```bash
node reset-pin.js "Your Name" --email you@example.com
```

Then on the login screen, *Admin: forgot PIN?* → enter that email → enter the 6-digit code it receives (valid 15 minutes, 5 tries, single use) and a new 4-digit PIN. This needs the mail account to be set up (below) — until then the screen says email isn't set up, and `reset-pin.js` above is the fallback. Only the Admin can use this, and the screen never reveals whether an email exists.

> Terminal tips for this host: paste one command at a time; if pasted text shows `^[[200~`, run `bind 'set enable-bracketed-paste off'` first; a new Terminal tab starts with no environment, so redo the `source …/activate` and `export` lines.

## Every later deploy

1. On your dev machine, after changing app code: `npm run build:cpanel` — regenerates `deploy/` (runs the web build with the production API URL and bundles the API).
2. Commit **including `deploy/`**, push to `main`.
3. cPanel → Git Version Control → **Update from Remote** → **Deploy HEAD Commit**.
4. Only if `deploy/api/package.json` changed (rare): Setup Node.js App → **Run NPM Install**, then **Restart**.
5. Only if `apps/api/prisma/schema.prisma` changed: in Terminal, `cd …/deploy/api`, export `DATABASE_URL`, `npm run db:push`. It refuses changes that would lose data; accept that deliberately with `npx prisma db push --accept-data-loss` after confirming it's fine, or migrate the data first. (This app has no Prisma Migrate history — `db push` is the tool in dev and production.)

If `git pull` complains about local changes on the server, the server's checkout has drifted — `git checkout -- .` on the tracked files, then pull again (never commit from the server).

## SSL
Once both subdomains' DNS points at this account, cPanel's AutoSSL (Let's Encrypt) issues certificates automatically.

## Using MySQL instead
Not wired up: the schema and `deploy/` are PostgreSQL-specific. It would need the provider swapped in `scripts/build-cpanel.mjs`, a `mysql://…` `DATABASE_URL`, and a check of the models for MySQL compatibility.
