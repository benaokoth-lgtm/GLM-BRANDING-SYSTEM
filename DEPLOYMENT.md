# Deploying to cPanel — api.glmgroup.co.ke + pos.glmgroup.co.ke

Two pieces are hosted, both **prebuilt and committed under `deploy/`** — nothing is built on the server:

| Folder | What it is | Where it runs |
|---|---|---|
| `deploy/api/` | One bundled `server.js` (shared code inlined), a tiny `package.json` (only `@prisma/client` + `prisma`), and the Prisma schema pre-set to PostgreSQL | cPanel **Setup Node.js App** → this folder is the *Application root* |
| `deploy/web/` | The static React build (API URL baked in) + `.htaccess` for client-side routes | Copied to the `pos.glmgroup.co.ke` document root |

**Why not build on the server?** cPanel's Node.js Selector replaces the app root's `node_modules` with a symlink into its own virtual env, which doesn't cooperate with this repo's npm-workspaces monorepo (npm sees one package and installs nothing). A slim, prebuilt app root is the layout the Selector is designed for. The monorepo itself is unchanged for local development.

## One-time setup

### 1. Database
cPanel → **PostgreSQL Databases**: create a database (no spaces in the name!), a user, and add the user to the database with all privileges. The connection string is:

```
postgresql://DBUSER:PASSWORD@127.0.0.1:5432/DBNAME
```

Use `127.0.0.1`, not `localhost` (this host rejects IPv6 `::1`). If the password contains `@ : / ? # %`, percent-encode those characters.

### 2. Git
cPanel → **Git™ Version Control** → Create: clone URL `https://github.com/benaokoth-lgtm/GLM-BRANDING-SYSTEM.git`, path `/home/glmgroup/repositories/glm-branding-pos-system`, branch `main`.

### 3. The API's Node.js App
cPanel → **Setup Node.js App** → Create (or edit) the application:

- **Node.js version**: 18 (or newer)
- **Application mode**: Production
- **Application root**: `repositories/glm-branding-pos-system/deploy/api`
- **Application URL**: `api.glmgroup.co.ke`
- **Application startup file**: `server.js`

**Environment variables — one row per variable, raw value only** (no `export`, no quotes, never several in one value):

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_URL` | the connection string from step 1 |
| `JWT_SECRET` | a long random string — generate once with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and keep it; changing it logs everyone out |
| `CORS_ORIGINS` | `https://pos.glmgroup.co.ke` |

No `PORT` — Passenger assigns it. Optional (each feature disables itself cleanly if unset): `SMTP_*` (**older installs only** — email is now set up in Master Data → Email) and the `MPESA_*` set (**older installs only** — M-Pesa is now configured in Master Data → M-Pesa instead; see `apps/api/.env.example`; `MPESA_CALLBACK_URL` must be `https://api.glmgroup.co.ke/api/mpesa/callback`).

Save, then click **Run NPM Install** (this installs Prisma and generates its client), then **Restart**.

cPanel → **Domains**: create `pos.glmgroup.co.ke`; its document root should be `/home/glmgroup/pos.glmgroup.co.ke` (what `.cpanel.yml` copies into). **Git Version Control → Pull or Deploy → Update from Remote → Deploy HEAD Commit.** This copies `deploy/web` into the subdomain and restarts the API (`.cpanel.yml`).

**Payroll now follows the Kenyan statutory rules — no database change.** Before, PAYE was charged on gross pay, and the *whole* 12% NSSF and 3% housing levy (the employee's and the employer's shares together) were taken from the employee's pay. Now, for an employee: **NSSF** is 6% of pay up to NSSF's Upper Earnings Limit for the pay date (KES 18,000 from Feb 2023, 36,000 from Feb 2024, 72,000 from Feb 2025, 108,000 from Feb 2026 — so at most 6,480 a month from Feb 2026), **SHIF** is 2.75% of gross pay (minimum KES 300) and the **Affordable Housing Levy** is 1.5% of gross pay; these three are deducted from gross pay first, **PAYE is charged on what is left** (taxable pay) by the monthly bands (10% to 24,000, 25% to 32,333, 30% to 500,000, 32.5% to 800,000, 35% above), less the KES 2,400 personal relief (never below zero). The **employer** matches NSSF (6%) and the housing levy (1.5%) *on top of* the pay: an extra cost, shown on the NSSF tab and on payslips, and booked as wages expense with the liability owed to NSSF and the levy fund — so the employee's net pay goes **up** compared with before, and wages expense in the books includes the employer's share. Everything is worked out when read, so **pay logged earlier is recalculated by the new rules** (the P9 and payslips follow). The rates and limits are constants at the top of `packages/shared/src/tax.ts` — **have your accountant check them against the current NSSF, KRA and SHA notices** (they change) and tell me if any differ. The P9 shows gross pay, NSSF, SHIF, housing levy, taxable pay, tax charged, personal relief and PAYE month by month.

**Freelancers own their clients while they keep bringing orders, and are paid to their M-Pesa phone — needs `npm run db:push` (VPS: `update.sh` does it).** (1) **Client ownership:** the first order credited to a freelancer makes the client theirs, and it stays theirs **for as long as they keep bringing orders** — every order restarts the count, and it lapses only after N months with none (Commission → Rates, default 12). While it is theirs, every order from that client is credited to the freelancer **whoever captures it, with no mark needed**; a staff claim on that client changes nothing, and neither staff nor another freelancer can take them. Marking an order for a freelancer now needs the client's name and phone (that is how the client is recognised next time). A suspended freelancer's clients are not credited to them; a manager can release a client (Commission → Freelancers → Freelance sales persons → *Clients they own*). (2) **Pay to their phone:** Freelancers → Weekly pay → an approved payout now offers *M-Pesa to their phone (automatic)* beside the by-hand methods. This is Safaricom's **B2C** service (an STK push can only ask a customer to pay *you*): the system asks Safaricom to pay the person's own M-Pesa number from your Paybill; the payout is marked Paid, and the expense booked under Freelance Commission, only when Safaricom's result arrives. While it is on its way nothing else can be done to the payout, so it can never be paid twice; a failure, refusal or timeout leaves it approved to try again. Amounts go out in whole shillings, Ksh 10 to 150,000 each. If Safaricom's answer never arrives, a manager settles the attempt by hand (not sent, or sent with its M-Pesa receipt code). **To set it up** (Master Data → M-Pesa → *Paying money out to a phone*): ask Safaricom to enable **B2C** on your Paybill (it is a separate Daraja product; a Till cannot send money); create an API **initiator** user in the M-Pesa organisation portal; paste the initiator name, its password and Safaricom's **.cer certificate** (Sandbox or Production, from the Daraja portal); press *Save* and *Test the connection*. The initiator password is sealed with the DATA_KEY. **Test in the Daraja sandbox first** (Environment: Sandbox, with the B2C test shortcode, initiator and certificate from the Daraja simulator page) before going live. This was built to Daraja's B2C specification and tested against a local stand-in for Safaricom, not against Safaricom itself — so make the first live payment a small one. The push adds `FreelanceClient`, `MpesaDisbursement`, the B2C columns on `MpesaSettings`, `FreelancePayout.receipt` and `CommissionSettings.freelanceOwnershipMonths`.

**Freelance sales persons — needs `npm run db:push` (VPS: `update.sh` does it).** People outside the staff who bring us work now have their own commission and account (Commission → **Freelancers**). (1) **At order capture** (General Order, Film, Artwork, and corporate quotations/invoices) the *Who brought this order?* choice gains *A freelance sales person brought this order*: pick one, or add a new one on the spot (name and phone are needed; M-Pesa number, National ID, KRA PIN and bank are optional). A phone number is one account. A new person added by staff waits for a manager's approval and is not paid until then; one added by a manager is active at once. (2) **One order, one owner:** an order is credited to a staff member OR a freelance sales person, never both. Choosing a freelancer clears any staff claim; a client already credited to a staff member cannot be given to a freelancer; and a freelance order earns no staff commission of any kind (no sourcing, film or artwork commission) and counts towards no staff sales target. (3) **Pay:** weekly (Monday to Sunday), in marginal bands on the week's net sales (VAT out) *received* on their orders — editable under Commission → Rates (the rates and what they apply to were changed afterwards: see "Freelancer commission no longer eats into base prices" below). Only lines sold **at or above base prices** count: the price-list price for services and stock items, the floor for film, the recommended price for artwork (a line discounted below base earns nothing; the rest of the order still counts). (4) **Weekly payouts:** Freelancers → *Weekly pay* → *Approve week* (once the week has closed), then *Mark paid* by M-Pesa, bank, cash or petty cash; paying records an expense under the new **Freelance Commission** head (account 5025), so it reaches the books. Only an active freelancer is paid. Each person has an account page: paid to date, approved and waiting, not yet approved. With the commission scheme off, a freelance mark is ignored (as a staff claim is). The push adds the `FreelanceAgent` and `FreelancePayout` tables, `Order.freelanceAgentId` / `freelanceQualifyingShare`, and `CommissionSettings.freelanceBandsJson`. (Withholding tax is now deducted — see the next paragraph.)

**Freelancers are paid by any method, and withholding tax is deducted — needs `npm run db:push` (VPS: `update.sh` does it).** (1) **Any payment method:** a freelancer's payout can be paid by **M-Pesa (sent to their phone, or by hand), cash, cheque, bank transfer, card or petty cash** — there is no restricted method. Each person has a *usual way of being paid* (set when adding or editing them) that is pre-selected, but any method can be chosen for any payout, with a **payment reference** (cheque number, bank or M-Pesa reference). **Cheque** is now also offered for ordinary expenses, supplier payouts and staff commission payouts, and books to the bank account like a bank transfer. (2) **Withholding tax:** tax is deducted from each freelancer's commission before they are paid. The **standard rate is a 5 % placeholder — confirm the rate and the due date with your accountant** and change it under Commission → Rates; a person can have their **own rate** (Freelance sales persons → Edit; **0 = exempt**, e.g. holds an exemption certificate). The tax is worked out and **frozen when the week is approved** (so a later rate change does not alter an approved payout), the weekly table shows *Commission / Tax withheld / To pay*, and what is paid out — by any method, including the M-Pesa B2C send — is the **net** amount. In the books the expense is the full commission; the cash/bank/M-Pesa account is credited the net and the tax is held as a liability in **Withholding Tax Payable (2240)**. Freelancers → **Tax withheld** lists each month's payments with the person's KRA PIN, commission, rate, tax and net (people with no KRA PIN are flagged). When you pay the tax over to KRA (iTax), record it in Accounting as a journal: debit Withholding Tax Payable, credit the bank. **Not built:** withholding certificates for the freelancer, and any minimum-amount threshold below which no tax is withheld (set that person's rate to 0 if needed). The push adds `FreelanceAgent.payMethod` / `whtRate`, `FreelancePayout.withholdingRate` / `withholdingTax`, `Expense.withholdingTax` and `CommissionSettings.freelanceWhtRate`.

**Freelancer commission no longer eats into base prices: a small band on the base price, plus a share of the premium — needs `npm run db:push` (VPS: `update.sh` does it).** The weekly bands used to apply to the whole sale, including the base-price part where our margin is thinnest. Now a freelancer's commission has two parts. (1) **Bands on the base-price part only** — the price-list price (the floor for film, the recommended price for artwork) — now **2% / 3% over 50,000 / 4% over 150,000** per week (editable under Commission → Rates; these are starting figures: keep each rate at or below about a fifth of the margin you actually make at base price, i.e. rate ≤ margin × 0.2). (2) **A share of what was charged above base** — default **30%** (Rates → *Freelancers: % of the amount charged above base that they keep*): a job costs the same whatever it is sold for, so the extra is nearly all profit and the company keeps the other 70%. (3) **Contracted-out services and stock resale** carry a thin mark-up, so the base part of those lines counts at a reduced weight towards the bands — default **50%** (Rates → *Contracted-out and stock lines count at this %*; 100 = no reduction); any amount above base on them is still shared in full. A line sold below base still earns nothing. The weekly table shows *Base-price sales*, *Charged above base* and the commission split ("bands + above base"); withholding tax and every payment method work on the total as before. The split is worked out and stored on each order when it is captured (`Order.freelanceBaseShare`, `freelanceLowShare`, `freelancePremiumShare`); the rates are read when the week is worked out, so unapproved weeks follow a rate change and approved weeks keep their figures. The push adds those three order columns and `CommissionSettings.freelancePremiumPct` / `freelanceLowMarginPct`. **Existing settings:** if a Rates screen was already saved with the earlier 3% / 5% / 7% bands, those stay until you change them — review them. Orders captured before this change count wholly as base price (no premium).

**Missed sales target: no commission on that month's sales, no roll-over; artwork is the exception — no database change.** A month stands alone: if a person's net sales received do not reach the target (3 × basic salary), they earn no sales-based commission for that month (sourced-client bands and the film premium), and nothing carries over to the next month. **The artwork extra** (the amount charged above the recommended price, at the artwork percentage, VAT out, earned as the customer pays) is now **paid whether or not the target was met**; artwork sales still count towards the target. Before this change artwork was held with the film premium. The Commission pages now say "earned on film but not paid" instead of "held", and the artwork line is always in the total. A person with **no salary recorded** still has their sales commission and film premium on hold (shown, not paid) until a salary is recorded, but their artwork extra is paid. Approving a month freezes it, so months already approved keep their figures; unapproved months are recalculated.

**Walk-in orders always print on the thermal receipt printer, two copies — no database change.** When a General, Film or Artwork order is captured, it prints as the 80 mm thermal receipt in **two copies, one labelled CUSTOMER COPY and one PRODUCTION COPY**, whether it was paid in full or not (before, one left with a balance printed as an A4 invoice). An order that still owes a balance shows **INVOICE — BALANCE DUE** with a *pay by* date and the balance, because in the background it is already an invoice (status Invoice, due 7 days out): later payments are taken against that same invoice and the balance falls until it is settled, and it stays an invoice, tracked through production to handover. A **quotation** that is paid for (a deposit or in full) becomes an invoice, and an invoice **created from scratch** (a corporate client's) stays an invoice, as before; both print on A4. On an order's detail window, *Print receipt (2 copies)* reprints the thermal slips, and a walk-in invoice also has *Print invoice (A4)* for a full-page copy; email and WhatsApp still send the invoice layout.

**A register of freelance sales persons to pick from at order capture — no database change.** The register is now under **Master Data → Freelancers** as well as Commission → Freelancers → *Freelance sales persons & accounts*: the same list, where a manager adds, edits, approves, suspends and opens each person's account. Each person has a **register number, FL-001, FL-002 …**, taken from their record number (so it never changes and needs no setup for people already added). At order capture the *Who brought this order?* choice is now a **search box** instead of a long drop-down: type part of a **name**, an **FL number** or a **phone number** (written as 0712 345 678 or in part) and pick from the matches; the chosen person shows with their FL number and a *Change* button, and *+ A new freelance sales person…* adds someone on the spot as before. Staff see only the name, FL number and last three digits of the phone (never pay or bank details); a suspended person cannot be picked. > Terminal tips for this host: paste one command at a time; if pasted text shows `^[[200~`, run `bind 'set enable-bracketed-paste off'` first; a new Terminal tab starts with no environment, so redo the `source …/activate` and `export` lines.

## Every later deploy

1. On your dev machine, after changing app code: `npm run build:cpanel` — regenerates `deploy/` (runs the web build with the production API URL and bundles the API).
2. Commit **including `deploy/`**, push to `main`.
3. cPanel → Git Version Control → **Update from Remote** → **Deploy HEAD Commit**.
4. Only if `deploy/api/package.json` changed (rare): Setup Node.js App → **Run NPM Install**, then **Restart**.
5. Only if `apps/api/prisma/schema.prisma` changed: in Terminal, `cd …/deploy/api`, export `DATABASE_URL`, `npm run db:push`. It refuses changes that would lose data; accept that deliberately with `npx prisma db push --accept-data-loss` after confirming it's fine, or migrate the data first. (This app has no Prisma Migrate history — `db push` is the tool in dev and production.)

If `git pull` complains about local changes on the server, the server's checkout has drifted — `git checkout -- .` on the tracked files, then pull again (never commit from the server).

## SSL
Once both subdomains' DNS points at this account, cPanel's AutoSSL (Let's Encrypt) issues certificates automatically.

## Using MySQL instead
Not wired up: the schema and `deploy/` are PostgreSQL-specific. It would need the provider swapped in `scripts/build-cpanel.mjs`, a `mysql://…` `DATABASE_URL`, and a check of the models for MySQL compatibility.
